# Naming the picross puzzles

The 137 pictures in the bank have ids (`JANKO222`), not names. Card #390 item 7
is that the win screen should show a NAME, and that Mario writes all 137 of them
himself. This is the tool he writes them in and the file it produces.

- The tool: **`site/picross-names/`**, live at
  `https://crossplay.ma-r-s.com/picross-names/`.
- The data it runs on: `site/picross-names/data.js`, GENERATED by
  `tools_local/picross/gen_name_tool.py` from the bank and the font headers.
- The answer it produces: `names.txt`, described below.

The page is deliberately not linked from anywhere and carries
`robots: noindex`. It is a working tool for one person doing one job once, not
a page of the site.

## Why a page on the site rather than a local file

He said he would be doing this "on the sofa", over several sittings, on whatever
device is to hand. A `file://` page is a laptop-only tool: getting one onto a
phone means a checkout or an AirDrop, and doing forty of these on a phone is the
case that has to work. A URL is the only form that opens the same on both.

Everything still happens in the tab. There is no network call, no upload, and no
server side: the puzzles are in `data.js`, the answers are in `localStorage`.

## Where the work actually lives, and how it is lost

**In `localStorage`, under `crossplay.picross.names.v1`, in that browser on that
device.** Every commit writes it synchronously before anything on screen moves,
and the half-typed word in the field is written too, so a tab closed mid-name
loses nothing.

What that survives: closing the tab, closing the browser, rebooting, going
offline.

What it does NOT survive, and both of these are real:

- **Another device or another browser.** Forty names typed on the phone are on
  the phone. Moving them is a manual step: **Download the save file** on one
  device, **Load a save file** on the other. The load MERGES rather than
  replaces (newer timestamp wins per puzzle), so it is safe in either direction
  and safe to do repeatedly.
- **Clearing site data**, or Safari's own eviction of storage for a site not
  visited for a long time.

If the browser refuses to store at all (a private window, storage disabled) the
tool says so where the "Saved" line usually goes, rather than pretending.

## The format it exports

`names.txt`, one line per **answered** puzzle:

    # comment lines start with a hash
    JANKO222<TAB>COCKTAIL GLASS
    JANKO230<TAB>

Three states, and the file distinguishes all three:

| state | in the file |
| --- | --- |
| named | its id, a tab, the name |
| deliberately unnamed (no good name exists) | its id, a tab, nothing after it |
| not answered yet | absent from the file entirely |

That third row is the reason a skipped puzzle writes nothing at all. "I have not
got to this one" and "this picture has no name" are different answers, and a
format that cannot tell them apart turns the second one into a gap in the data
instead of the finding it is.

Tab-separated to match `janko.txt`, which is the other hand-maintained picross
asset and which the generator already reads; a name may contain spaces and
never contains a tab.

**The save file is a different file** (`picross-names-save.json`) and is not the
answer: it is the tool's own state, including which puzzle he was on, and exists
to be carried between devices.

## What the tool knows that a text box does not

The win screen sets the name in `toybox::kDisplayFont` and puts it through
`toybox::fittedTitle`, so two things are true that a plain text box would let
him discover on the panel a week later:

**A character the cut has no glyph for draws as NOTHING.** Not a box, a hole:
`GfxRenderer` returns without drawing and without advancing the pen. `toybox_20`
and `toybox_30` carry U+0020..U+007E and nothing else, so `PIÑATA` reaches the
panel as `PIATA`. The tool refuses to file such a name, says which character did
it, and offers the folded spelling as a button. The preview box shows the word
with the hole in it, which is more convincing than the sentence.

Typographic punctuation is folded silently on the way in, exactly as
`utf8FoldTypography` folds prose, and for a specific reason: an iPhone turns a
typed apostrophe into U+2019 by itself, so without that every possessive he
typed would arrive broken. Letters are never folded silently, because an accent
folded away changes the word and that is his call.

**A name too wide for the display cut is set in a smaller one.** `fittedTitle`
walks toybox_30 -> toybox_20 -> toybox_10 and only ellipsizes when the smallest
still overflows. So there are four answers, not two, and the tool gives all
four: fits at full size, will be set one size down, will be set at the smallest
cut, or will be cut short. It measures the real proportional advance widths out
of the font headers -- counting characters cannot answer it, since `WWWW` and
`iiii` differ threefold.

The name is uppercased as it is typed, because every Toybox label is and because
the measurement has to be of the string that will really be drawn: capitals are
wider, so measuring what he typed and storing what the device gets would report
a fit that is not there.

## The band is measured, not derived

The width the fit is judged against is the rect `buildWin` really hands the
name. It is **448px today**, and that number is not typed anywhere by hand:

    tools_local/picross/measure_name_band.sh   # builds the win screen, prints the rect
    tools_local/picross/gen_name_tool.py       # rebuilds data.js from bank + fonts + that

`measure_name_band.sh` writes `tools_local/picross/name_band.txt` and
`gen_name_tool.py` reads it, refusing to run if it is missing. **Card #390
changes this screen** -- the size label goes, the designer credit goes, the name
arrives -- so whoever lands that should re-run both, in that order.
`host-tests/site/run.sh` fails if `data.js` no longer matches the bank, the
fonts and the recorded band, so a curated bank or a regenerated cut cannot leave
the tool quietly describing a screen that has moved.

## What the tool does not do

It does not write anything into the repository, and it does not know about the
firmware. Landing the names is a separate step: take `names.txt`, and let the
generator put the names into `PicrossPuzzles.h` beside the ids.

It also cannot tell whether a name is a GOOD name. The pictures were judged
legible at picker scale (`janko-selection.json`), not nameable; some of them
genuinely are not, which is what the "no good name" answer is for and why that
answer is data rather than a gap.
