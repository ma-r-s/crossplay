## What the earlier draft got wrong

The staged draft at the workspace root was written on 2026-08-31 against a
reading of the registry that no longer matches it. Four things changed:

1. **The metadata file is `firmware.json` under `firmwares/<id>/`**, not
   `integration.json` under `integrations/<id>/`. Unknown fields fail
   validation, so the old field set would have been rejected outright.

2. **The four-part package is not required.** The firmware guide says in so many
   words: "A single merged image starts at offset `0`." The published
   `crossplay-<v>-sticky-full.bin` is exactly that, so the release artifact can
   be submitted as-is. The draft's note 0 ("the parts have to come from a
   dedicated `pio run -e gh_release_sticky` ... Do not go looking again") was
   wrong, and following it would have meant shipping a hand-built binary instead
   of the one users can download and verify.

3. **There is no submission form on the Playground site.** The site links to the
   registry repository; every contribution is a pull request. This was checked
   on the live page, which carries "Contribute to Playground" pointing at the
   GitHub repo.

4. **A preview image is not required to be a device photo for a partner entry.**
   The pull request template asks that "community entries include author
   attribution and a real Sticky preview; partner entries use the official logo
   as identity artwork." The shared rules also reject renders outright, so a
   simulator screenshot was not an option regardless.

at card size; the two below it are a single mark each.

The tile's own caption underneath already carries the summary, so the image does
not need to repeat it, and one thing drawn large survives the shrink where four

about tile size: the wordmark is still fully legible there.

Jersey 25's capital V reads as a U to anyone who has not been told otherwise

docstring bans V from anything set in it. **CrossPlay has no V**, so the trap
does not apply to this artwork -- but it applies to any descriptor line someone
adds later.

## The hardware test, and how it was nearly reported wrong

The entry first went out with the four physical-device boxes unticked, because
the newest hardware verification anywhere in the repository or the memory files
was **v1.4.0 (2026-08-26)**, and no Sticky was attached to this machine.

That was a stale RECORD, not the state of the world: Mario had flashed
**1.12.11** to a Sticky and run it, and the fact lived only with him. It reached
this session relayed through the coordinator, who confirmed it with him directly
because the claim goes to a third party under his name.

Worth keeping, because the repository could not have told anyone this: **the
newest hardware verification is a fact about what Mario did last week, and
nothing in git records it.** Every written source here agreed on v1.4.0 and all
of them were behind. If a future session needs to know what has run on the
Sticky, the honest answer is to ask him, not to grep.

What the entry claims, arrived at over three rounds as Mario was asked
progressively more specific questions:

- **Round one**, all four boxes unticked. Every written source said v1.4.0 and
  no Sticky was attached to this machine.
- **Round two**, "he flashed it and tried it". That established boxes 1 and 2
  (installation, first boot and main workflow) and nothing more, so boxes 3 and
  4 stayed unticked: box 3 conjoins touch *and* the hardware buttons, box 4
  conjoins reboot, saved state, USB reconnection *and* repeated installation.
- **Round three**, he confirms he used the physical buttons and restarted the
  device. Box 3 is now fully established. Box 4 is ticked on its "where
  applicable" qualifier, with the pull request saying in plain words that the
  reboot clause is what he confirmed and that USB reconnection, a repeated
  install, and saved state across that particular restart were not re-checked
  at 1.12.11.

**The lesson is the shape, not the outcome.** Each round the answer got more
specific because the question did. "Has it been tested?" would have produced a
yes and four ticks that meant nothing; "did you use the buttons, did you restart
it" produced something Seeed can weigh. The entry says who verified what, so a
reader can tell a tick that means "we ran it" from one that means "we assume
it".

**Provenance, and it stays recorded.** All of this reached the session relayed
rather than from Mario directly, and a past flash leaves no trace anyone here
can read. It is not independently verifiable by this session or the one that
asked him. The workspace rule about relayed claims exists for exactly this
shape, and the claim is public, under his name, to a partner.
